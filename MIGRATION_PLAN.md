# Claude Code Auth Switching Migration Plan

## Correction (2026-07-20)

Phase 1 shipped setup-token auth as the interactive path. That was wrong and has
been replaced by per-profile `CLAUDE_CONFIG_DIR` with native logins.

What the token approach actually did, verified on Claude Code 2.1.215:

- `CLAUDE_CODE_OAUTH_TOKEN` overrides the interactive keychain login rather than
  supplementing it. `auth status` reports `authMethod: oauth_token` with no
  email and no `subscriptionType`, and the TUI header reads "Claude API".
- The keychain credential is shadowed, not deleted, so `/login` succeeds but
  only for the current process. The installed `claude()` wrapper re-injected the
  token on every launch, so the login never persisted. This read to the user as
  "it logs me out every time I run my command".
- Those sessions were billed as API usage rather than against the Max plan.

The plan's premise conflated two separate things. Copying credential blobs and
guessing keychain service names was genuinely broken and is still off the table.
`CLAUDE_CONFIG_DIR` itself was never broken. Claude Code still keys credential
storage per config dir:

```text
~/.claude          -> Claude Code-credentials
~/.claude-<name>   -> Claude Code-credentials-<first 8 hex of sha256(path)>
```

Confirmed: `sha256("$HOME/.claude-cc1")[0:8]` = `150abde7`, which is exactly the
existing keychain item for that profile. So a profile can hold its own native
login with no copying and no service-name guessing — cc-switch sets the config
dir and Claude Code manages its own credential.

Setup-token auth is retained for headless/CI use only, behind an explicit
`run --token` flag.

## Context

`cc-auth-switcher` and `cc-rate-balancer` currently depend on implementation details that are no longer stable enough on macOS:

- `cc-auth-switcher` switches accounts by copying Claude Code credential blobs between the default `~/.claude` profile and profile-specific locations.
- On macOS, those blobs are stored in Keychain. The old implementation guessed Claude Code's profile-specific Keychain service naming for `CLAUDE_CONFIG_DIR`.
- `cc-rate-balancer` probes rate limits by starting an interactive Claude Code TUI in tmux and scraping the rendered status line.

Current Claude Code documentation describes macOS credentials as Keychain-managed, while `CLAUDE_CONFIG_DIR` credential-file behavior is documented only for Linux and Windows. For scripts and CI, the supported per-process auth path is a long-lived OAuth token generated by `claude setup-token` and passed through `CLAUDE_CODE_OAUTH_TOKEN`.

Claude Code also documents structured rate-limit fields in status-line JSON:

- `rate_limits.five_hour.used_percentage`
- `rate_limits.five_hour.resets_at`
- `rate_limits.seven_day.used_percentage`
- `rate_limits.seven_day.resets_at`

References:

- https://code.claude.com/docs/en/iam
- https://code.claude.com/docs/en/statusline
- https://code.claude.com/docs/en/agent-sdk/python

## Goals

1. Stop relying on Claude Code's private macOS Keychain storage details.
2. Preserve simple named-account workflows for interactive use.
3. Preserve a plain `claude` workflow through an explicit wrapper or shell function.
4. Give `cc-rate-balancer` a stable way to run Claude Code under a selected account.
5. Replace rendered TUI scraping with structured rate-limit data.
6. Keep profile tokens out of shell history and repo files.
7. Make failure modes fail closed: never overwrite a good profile with logged-out or invalid auth state.

## Non-Goals

- Do not copy or edit Claude Code's private credential blobs.
- Do not write to Claude Code's keychain items directly.
- ~~Do not depend on `CLAUDE_CONFIG_DIR` for account auth on macOS.~~
  Superseded 2026-07-20. `CLAUDE_CONFIG_DIR` is the supported interactive path;
  setting it and letting Claude Code own the credential requires no blob copying
  and no service-name guessing. See the Correction section.
- Do not resume automatic force-swapping on probe failure by default.
- Do not solve Remote Control multi-account switching in this migration. `CLAUDE_CODE_OAUTH_TOKEN` tokens are documented as inference-only and cannot establish Remote Control sessions.

## Target Architecture

### Auth Model

Each account profile stores a `claude setup-token` OAuth token managed by `cc-auth-switcher`, not by Claude Code.

On macOS, profile tokens should be stored in Keychain under service names owned by this project, for example:

- service: `cc-auth-switcher-token`
- account: `<profile-name>`

The token is read only when launching Claude Code, then passed to the real Claude Code binary as:

```bash
CLAUDE_CODE_OAUTH_TOKEN=<token> claude "$@"
```

The default Claude Code Keychain login may still exist, but it is no longer part of switching.

### Profile Model

Profiles become metadata plus a token:

```text
profile name
token location
optional display label
optional notes
last validated timestamp
last validation result
```

The old `~/.claude-<name>` directories are no longer needed for Claude account auth. They may be kept temporarily during migration for backup and rollback only.

### Launch Model

`cc-switch` owns account selection and launches the real Claude Code binary.

Planned command surface:

```bash
cc-switch token add <name>       # store a pasted setup-token token
cc-switch token remove <name>    # delete stored token
cc-switch token list             # list profiles without printing tokens
cc-switch validate <name>        # run a low-cost auth validation
cc-switch run <name> [args...]   # exec Claude with that profile token
cc-switch use <name>             # set active profile marker
cc-switch run-active [args...]   # exec Claude with active profile token
cc-switch list                   # show configured profiles and validation state
```

Named aliases become:

```bash
alias cc1='cc-switch run cc1'
alias cc2='cc-switch run cc2'
```

Plain `claude` support should be explicit, either as a shell function:

```bash
claude() {
  cc-switch run-active "$@"
}
```

or as an installed wrapper earlier in `PATH` than the real Claude Code binary. The shell function is safer for a first version because it avoids shadowing the real binary globally.

`cc-switch use <name>` changes the active profile marker. It does not mutate Claude Code credentials.

### Real Claude Binary Resolution

`cc-switch` must avoid recursive calls when `claude` is wrapped.

It should resolve and persist the real Claude Code binary path during setup, preferring:

1. `CC_SWITCH_CLAUDE_BIN` if set.
2. A configured path in `~/.cc-switch/config.json`.
3. Known install paths, excluding the wrapper path:
   - `~/.local/bin/claude`
   - `/usr/local/bin/claude`
   - `/opt/homebrew/bin/claude`

The resolved path should be visible in `cc-switch doctor`.

## Migration Phases

### Phase 0: Containment

Status: partially done.

Keep the current system from making the situation worse.

Acceptance criteria:

- `cc-switch swap <name>` refuses to save logged-out default auth into a profile.
- `cc-switch warm` refuses to sync logged-out default auth into a profile.
- `cc-rate-balancer` does not force-swap on probe failure unless explicitly configured.
- Launchd jobs are stopped while credentials are known-bad.

### Phase 1: Token-Backed Auth Switching

Status: SUPERSEDED 2026-07-20. Implemented, then replaced by config-dir auth
after live testing showed token auth cannot carry a subscription interactively.
See the Correction section. The task list below is kept for history; the token
machinery still exists but is reachable only via `run --token`.

Tasks:

1. Add a small profile store to `cc-switch`. Done.
2. Add Keychain helpers owned by `cc-auth-switcher`. Done.
3. Add `cc-switch token add/remove/list`. Done.
4. Add `cc-switch run <profile> [args...]`. Done.
5. Add `cc-switch use <profile>` and `cc-switch run-active [args...]`. Done.
6. Add a shell function installer for active-profile `claude`. Done.
7. Add `cc-switch doctor`. Done.
8. Update README for setup-token based auth. Done.

Initial migration flow:

```bash
# Keep current launchd jobs stopped.
claude setup-token
cc-switch token add cc1

# Log into the second account in browser when setup-token asks.
claude setup-token
cc-switch token add cc2

cc-switch validate cc1
cc-switch validate cc2
cc-switch use cc1
cc-switch run-active auth status
```

Validation strategy:

- Prefer `claude auth status` under `CLAUDE_CODE_OAUTH_TOKEN` if it reports token auth reliably.
- If `auth status` is insufficient, use a minimal non-interactive prompt and check for authentication errors.
- Validation must not print token material.

Failure behavior:

- If token validation fails, leave stored token untouched and mark the validation result failed.
- If `run <profile>` cannot read a token, exit non-zero before launching Claude.
- If the profile is unknown, exit non-zero.

Security requirements:

- Never print tokens.
- Never store tokens in repo files.
- Never write tokens into shell rc files.
- Prefer Keychain storage on macOS.
- For non-macOS fallback, use a `0600` file under `~/.cc-switch/`.

### Phase 2: Token-Aware Rate Balancer Launching

After Phase 1, `cc-rate-balancer` should stop invoking `cc-switch swap` for auth mutation.

Tasks:

1. Change balancer config to reference profile names managed by `cc-switch`.
2. Replace active account swapping with `cc-switch use <profile>`.
3. Run probes as `cc-switch run <profile> ...` or a dedicated `cc-switch probe-rate-limits <profile>`.
4. Stop copying credentials during snapshots.
5. Keep the active-profile marker as the shared source of truth.

Acceptance criteria:

- Balancer never mutates Claude Code credentials.
- Balancer never needs `CLAUDE_CONFIG_DIR` for account switching.
- Balancer can probe any configured profile without changing the active interactive profile, unless explicitly asked to switch active.

### Phase 3: Structured Rate-Limit Probing

Replace tmux rendered-status scraping.

Preferred options, in order:

1. A status-line JSON capture probe using the documented `rate_limits` fields.
2. A small Agent SDK probe that listens for `RateLimitEvent`.
3. A temporary compatibility fallback to TUI scraping, disabled by default.

Status-line probe sketch:

```bash
tmpdir="$(mktemp -d)"
capture="${tmpdir}/status.json"
status_script="${tmpdir}/statusline.sh"

cat > "$status_script" <<'SCRIPT'
#!/usr/bin/env bash
cat > "$CC_RATE_LIMIT_CAPTURE"
SCRIPT
chmod 700 "$status_script"

settings="$(jq -n --arg cmd "$status_script" '{statusLine:{type:"command",command:$cmd,padding:0}}')"

CC_RATE_LIMIT_CAPTURE="$capture" \
  cc-switch run "$profile" -p "hi" --max-turns 1 --settings "$settings" >/dev/null

jq '.rate_limits' "$capture"
```

This must be tested after Phase 1 restores working auth. If print mode does not run status-line commands after successful auth, use the Agent SDK event path instead.

Acceptance criteria:

- Probe returns 5h and 7d used percentages.
- Probe returns 5h and 7d reset timestamps.
- Probe errors are distinguishable from rate-limit exhaustion.
- Probe failure never triggers account switching by itself.

### Phase 4: Cleanup and Compatibility Removal

Tasks:

1. Remove profile symlink creation from new-account flows.
2. Keep a one-time migration helper for old `~/.claude-<name>` profiles.
3. Remove direct references to Claude Code Keychain service names.
4. Remove or quarantine old warm/swap behavior.
5. Update docs and tests to reflect token-backed switching.

## Compatibility Notes

### Existing `cc-switch swap`

`swap` should become a compatibility alias for `use`, not a credential-copy operation.

Status: done in Phase 1.

Proposed behavior:

```bash
cc-switch swap cc2
# writes active profile marker only
# prints that plain claude requires the installed shell function/wrapper
```

### Existing Profile Aliases

Old aliases like:

```bash
alias cc1='CLAUDE_CONFIG_DIR=~/.claude-cc1 claude'
```

should be replaced with:

```bash
alias cc1='cc-switch run cc1'
```

### Token Warming

Token warming should be removed or redesigned.

`claude setup-token` tokens are documented as long-lived one-year tokens. They do not need the old OAuth refresh behavior that the warmer was trying to preserve.

If validation freshness is still useful, replace warming with a low-frequency `cc-switch validate --all` job that records status but never rewrites token storage.

Status: old warming is disabled in Phase 1. `cc-switch warm` now runs
`cc-switch validate --all`; `warm-setup` refuses to install the old job.

## Open Questions

Answered 2026-07-20 on Claude Code 2.1.215:

1. Does `claude auth status` report `CLAUDE_CODE_OAUTH_TOKEN` as logged in?
   Yes — `loggedIn: true`, `authMethod: oauth_token`, but with no `email` and no
   `subscriptionType`. It is a distinct identity, not the subscription account.
2. Should plain `claude` be a shell function or a wrapper binary?
   Shell function. It is reversible by deleting one rc line, and `run-active`
   falls back to `~/.claude` so the wrapper can never strand the user.
3. Should old `~/.claude-<name>` directories be archived?
   No — they are now the mechanism, not legacy. Each holds a profile's login.
4. Should `cc-switch token add` accept stdin?
   Both: interactive paste when on a TTY, stdin otherwise.

Still open:

5. Does print mode run a configured status-line command after successful auth?
6. If not, is the Agent SDK available locally, or should `cc-rate-balancer`
   vendor a small Node/Python probe?
7. Setting `CLAUDE_CONFIG_DIR=~/.claude` explicitly is not identical to leaving
   it unset: auth still resolves and `subscriptionType` is correct, but `email`,
   `orgId`, and `orgName` come back `null`. `cc-switch` works around this by
   leaving the variable unset for the `default` profile. Worth confirming
   whether that is intended Claude Code behavior.

## First Slice Definition

The first slice is Phase 1 only.

Done means:

- Two profiles can be stored with setup-token tokens.
- `cc-switch run cc1 -p "hi" --max-turns 1` authenticates as `cc1`.
- `cc-switch run cc2 -p "hi" --max-turns 1` authenticates as `cc2`.
- `cc-switch use cc1` plus the shell function makes plain `claude` launch under `cc1`.
- No command copies or mutates Claude Code's macOS Keychain credential blobs.
- Existing launchd balancer jobs remain stopped until Phase 2 and Phase 3 are complete.

## Rollback

Rollback for Phase 1 is simple because it should not mutate Claude Code credentials:

1. Remove the shell function or wrapper.
2. Delete `~/.cc-switch/config.json` if created.
3. Delete `cc-auth-switcher-token` entries from Keychain.
4. Run the real Claude Code binary directly and `/login` normally.

Do not re-enable the old warm/swap launchd jobs unless they have the containment guards.
